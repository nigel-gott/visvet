Good instinct to ask, but no, here it's the right thing to do. The standard library stays out of it for one reason: symlinks. On a real disk, if 'a/b' is a symlink to somewhere else, 'a/b/..' is NOT 'a', so a general-purpose library can't safely resolve '..' by just looking at the text.
We don't work on the disk, we work on git's list of repo paths, partly from an old commit that isn't checked out. In git, a path is just text (git stores a symlink as a small file, it doesn't follow it), so resolving '..' as text is exactly the right meaning for us.
And we can't avoid needing it: four places turn a path written relative to one file into a repo path, which is how they find the box an arrow points to:
- TypeScript imports (`import x from '../model'`)
- Markdown links (`[review](../src/review.rs)`)
- Rust `mod` / `use crate::` paths
- ts-rs `export_to` paths (the 'generates' arrows)
So it's a real need that std deliberately leaves to the caller. Still your call between our 9 lines and `path-clean`; I lean to keeping ours, since it's tiny, tested and avoids a dependency.
