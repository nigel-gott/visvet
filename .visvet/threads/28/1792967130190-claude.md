Fair, I jumped to features. The underlying models I can see:

1. **Issues are files in the repo (your idea).** e.g. `issues/v0.2/split-mapview.md`: a folder is a milestone or epic, and nesting is breaking work down. The map draws them like code, so you zoom into a milestone the way you zoom into `src/`. An issue links to code by naming boxes in its text (`ui/src/Graph.tsx::mapView`), which becomes an **about** arrow, and to other issues (**blocks**). Threads work on issue boxes for free. Status sits in a short header (`status: open`). Git-first and multiplayer by default, and `visvet` mostly needs one new arrow detector, like the codegen ones.
2. **Issues hang off code.** An issue is a kind of thread on a box (my earlier list). Simpler, but no hierarchy or milestones, and an issue that isn't about code has nowhere to live.
3. **Two maps side by side.** A plan map (milestones → issues) next to the code map, with arrows crossing between them. Same files as 1, but shown as their own layer instead of mixed into the folder tree.
4. **Issues come from the code.** `TODO`/`FIXME` comments and debuffs become issue nodes. No bookkeeping, but only small, local things.
5. **An outside tracker is the truth.** GitHub or Forgejo issues, projected onto the map. Familiar, but not git-first, and the hierarchy is weak.

I'd go with **1**, maybe shown as **3** later: issues become ordinary Markdown files, and visvet only learns to read their links. Does 1 match what you had in mind?
