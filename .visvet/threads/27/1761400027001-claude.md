Agreed on both. Options, roughly in order of how git-first they are:

**Where threads live**

1. **Files in the repo (my pick).** e.g. `.visvet/threads/`, committed with the code. Push/pull is the sync, they travel with the PR, and future humans and AIs find them next to the code. Cost: thread changes show up in PR diffs.
2. **A side branch** (like `gh-pages`): same files on their own branch, which visvet commits and pushes for you. No noise in code diffs, but one more branch to sync, and it doesn't travel with a PR.
3. **git notes** (`refs/notes/visvet`): built into git and kept out of the tree, but tied to commits rather than boxes, merge badly, and GitHub doesn't show them.
4. **GitHub PR comments.** Multiplayer and notifications for free, but only on changed lines of an open PR. Folders, arrows and unchanged code have nowhere to go, and it needs the network and `gh`. Forgejo has a different API. Better as a one-way mirror later than as the store.
5. **In the code itself.** Fine for the *outcome* of a thread (a doc comment, a rename), not for the conversation; a chat in comments would clutter the code.

**Format, if files** (1 or 2)

- **One file per message**, e.g. `.visvet/threads/<thread>/<time>-<author>.md`. Two people replying at once never conflict in git, since nobody edits the same file.
- **Markdown** with a short header (box, author, kind), readable on GitHub and by any AI without visvet.
- **Random thread ids** instead of #1, #2…, since two people would both make #28. They'd show shortened, like `#k3f9`.
- **Authors become people** (your git name), plus the AI, instead of just you and me.
